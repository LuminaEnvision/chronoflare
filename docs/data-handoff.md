# Current application data handoff

The primary app consumes the **approved real-data export**, not the original
synthetic package. Scientific status is [Plan A for the scoped Pantanal v2](validation-report.md).
The exact contract is [observation-app-export-contract.md](observation-app-export-contract.md),
implemented by `app/src/data/observations.ts` and
`science/scripts/export_harmonized_series.py`.

## Active published files

- `app/public/data/observations/v1/manifest.json`: region, fixed solar offset,
  quality/dedup versions, source hashes, approval/model identity and year assets.
- `app/public/data/observations/v1/YYYY.json`: one row per acquired solar date,
  separate native Terra/Aqua/S-NPP day/night turns, and a non-null harmonized
  object only under the owner's complete-platform scope.
- `app/public/data/research-summary.json`: display-only evidence, counts and
  sample roles, generated by `scripts/export-research-evidence.ts`.
- `app/public/data/harmonization-pairs.json`: paired-chart display values,
  generated by `scripts/export-harmonization-pairs.ts` from committed evidence.

There are 4,318 acquired dates in 14 years and 635 published estimates. The owner
[decision record](../science/configs/harmonization_decision.json) binds approval
to the frozen model. No new manual download or new scientific delivery is needed
to serve those committed assets.

Native dates retain their original fixed regional solar reference. Harmonized
Terra night uses the previous native date, explicitly recorded in the inputs.
Missing turns remain null; missing date rows mean not acquired. Positive turn
pairs do not prove cloud-free coverage. Native partial sums must remain labeled.
Intervals must not be altered to force the point estimate inside their bounds.

The runtime consumer checks model/scope, physical values, native-input agreement,
asset paths, unique ordered dates, exact byte counts and SHA-256. Exported data
must be regenerated through the approved exporter and reviewed, not hand-edited.
Do not rerun the single-use independent score to rebuild the application.

## Separate datasets that remain available

- `app/public/data/v1/` and `app/src/data/schema.ts`: the **legacy synthetic demo**
  contract. Its baseline/anomaly/coverage examples are not new scientific results.
- `app/public/data/experimental/v1/`: a frozen August 2020 raw solar preview with
  an unapproved optional filter and no deduplication; see [preview scope](experimental-solar-calendar.md).
- The [detection explorer](detection-explorer.md): a separate unreviewed August
  2020 delivery with a verified IBGE 2025 Pantanal subset and optional GIBS/
  MapBiomas context. It is not the exact input behind every calendar cell.

H3 fire aggregates and approved seasonal/anomaly statistics are not implemented
by the current publication. The original [blueprint](blueprint-v1.2.md) records
that proposal, not a claim that all planned outputs exist.

## Verification and regeneration

```sh
npm run language:check
npm test
npm run test:science
npm run build
```

`npm test` includes reconciliation of every committed real year asset against
its hash, count, approval and research sidecar. `npm run data:validate` and its
`--real` option inspect the **legacy `data/v1` package**; they do not certify the
new default real-data contract. A fixture/pending result from that command is
expected for the separately retained demonstration.

Only the display sidecars can be regenerated from committed public evidence:

```sh
node --import tsx scripts/export-research-evidence.ts
npm run evidence:pairs
```

The scientific exporter additionally needs the source reconstruction artifacts;
its approved inference command is documented in the [v2 record](harmonization-v2-candidate.md).
Source acquisition, frozen fitting, one-time evaluation, human approval and
publication are separate operations. No data download or model fit occurs in
the browser or during the ordinary frontend build.
